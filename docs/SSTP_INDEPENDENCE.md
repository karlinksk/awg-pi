# Архитектурный инвариант: MikroTik SSTP независим от Raspberry Pi

**Зафиксировано 13 октября 2026 года для AWG Pi Gateway v1.3 и дальнейшей разработки.**

## Топология и ответственность

- **MikroTik ↔ облачный MikroTik (SSTP):** соединение поднимается и поддерживается непосредственно MikroTik. SSTP transport endpoint, логика соединения, авторизация, keepalive и маршрут до SSTP-сервера **не должны зависеть от Raspberry Pi, Mihomo, awg0 или таблицы 100 Pi**.
- **Raspberry Pi:** отдельный транспорт для клиентского Transit / Backup VPN через Mihomo и AmneziaWG. Перезапуск, отключение питания, обновление и откат Pi не должны разрывать SSTP *как туннель*.
- **Маршрутизация трафика клиентов:** это отдельная задача. Политика MikroTik может направлять различные назначения через SSTP либо через Pi. Недоступность Pi способна влиять на клиентские потоки, но не должна разрушать установленный SSTP.
- **AUTO SMART:** только SHADOW_ONLY до явного утверждения и проверки.

## Инварианты внедрения

1. Stage34+ не выполняет **никаких** команд конфигурации MikroTik, не меняет его SSTP-интерфейс, default route, правила mangle, NAT и policy routing. Отсутствие команд к MikroTik — сознательная граница проекта, не упущение.
2. Весь подлежащий изменению state находится на Pi; при сбое Pi само SSTP-соединение остаётся на MikroTik. Восстановление Pi не нуждается в SSTP для доступа к локальной recovery-копии.
3. Для клиентских назначений, отнесённых к Pi Transit, действует **FAIL-CLOSED**. Не допускается аварийный пропуск защищённого трафика через DIRECT.
4. IP endpoint всех candidate-нoд Mihomo должны использовать проверенную независимую DIRECT-underlay маршрутизацию. Нельзя допускать рекурсивного Pi-VPN-over-Pi-VPN или петли через SSTP без явной отдельной политики.
5. За фактическую независимость SSTP отвечает конфигурация MikroTik: при будущих работах с его маршрутизацией отдельно проверить DIRECT-путь к облачному SSTP-серверу, условия формирования сессии и отсутствие policy route через Pi. **Тесты Pi не доказывают конфигурацию MikroTik.**
6. Запрет на ненужную перезагрузку/переконфигурацию MikroTik сохраняется. Проверка восстановления Pi допускается только после подготовки безопасного отката Pi, но не требует искусственного отключения SSTP.

## Контрольный тест

- Read-only на MikroTik: SSTP connected, underlay cloud endpoint не зависит от Raspberry Pi.
- На Pi: фиксируем независимый доступ управления, здоровье интерфейсов и FAIL-CLOSED.
- При контролируемом выключении/перезагрузке Pi: наблюдаем, что SSTP на MikroTik остаётся connected; допускаем изменения маршрутизации только клиентского Transit согласно политике.
- После восстановления Pi: валидируем Mihomo/AWG, DIRECT candidate endpoints, table100, nftables и PBR без изменения SSTP.

Эти проверки для реальной связки MikroTik/Pi должны выполняться при отдельном разрешённом супервизируемом тесте. Тестовый Stage34 использует только синтетический sentinel "mikrotik-sstp.fixture"; он подтверждает, что код восстановления его не изменяет, **но не проверяет реальный SSTP на MikroTik**.
