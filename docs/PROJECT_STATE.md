# AWG Pi Gateway — состояние проекта и согласованные решения

**Срез: 2026-10-18.** Документ — короткая точка входа для следующего разговора или инженера. Это **не** протокол успешных испытаний: актуальное состояние устройства нужно проверять отдельно. При изменении решений обновлять этот файл вместе с соответствующей задачей. Не публиковать приватные IP, ключи, адреса подписок и данные пользователя.

## 1. Главная цель и границы работ

Закончить **AWG Pi Gateway v1.3.0**: воспроизводимый шлюз для Raspberry Pi 4 / чистой Debian 13 ARM64 с двумя транспортами **AmneziaWG** и **Mihomo**. Инсталлятор должен сразу устанавливать всё необходимое, **включая FFmpeg/FFprobe, Stage18 Node.js и yt-dlp** и сами движки — даже если VPN-профиль/подписка будут внесены позднее. После ввода AWG-профиля и/или Mihomo-подписки система должна штатно подбирать пригодные ноды, работать после перезагрузки, сохранять политики и обеспечивать предусмотренный резервный путь.

**Работа над шлюзом важнее вспомогательных подсистем.** Не расширять резервирование, мониторинг, NAS, IPTV и административные инструменты ради них самих. Исправлять блокирующее, остальное записывать в отложенные задачи; не подменять основной план очередной подзадачей.

## 2. Принятая архитектура

- Режимы: **Selective = FAIL-OPEN**, **MikroTik Transit / Backup VPN = FAIL-CLOSED**. Transit не пропускает выбранный трафик DIRECT при отсутствии рабочего VPN; разрешён явно определённый статус `NO_WORKING_TRANSPORT`.
- **Mihomo — основной транспорт**, **AWG — резерв**, когда его рабочий профиль действительно настроен. Не считать AWG готовым только из-за установленного движка; не пытаться активировать незаполненный профиль.
- Mihomo-кандидаты проверяются по поддерживаемым типам транспорта/протокола, а не только VLESS. Hot Pool/READY: HTTPS-проверки OpenAI API и ChatGPT плюс **один реальный 24-кадровый декод YouTube**. Удалённая первичная HTTP/Range-проверка YouTube не должна снова становиться пропускным критерием. **Браузерная проверка ChatGPT не нужна.**
- Hot Pool работает изолированно от активной ноды и её сервера/алиасов; SHADOW-тесты не должны прерывать live-соединение. Успех локального proxy **не равен** успеху `mihomo0`/TUN и **не равен** передаче трафика клиента LAN. READY и переключение требуют адекватных postcheck и rollback, предотвращения колебаний.
- AUTO/резервирование транспорта: консервативная политика, не подменять приоритеты переключениями «ради скорости». Возврат с AWG на Mihomo не включать самовольно; окончательная автоматическая политика возврата требует явного подтверждения и практического теста (в прежних обсуждениях были разные варианты).
- DNS остаётся независим от VPN (DoH на MikroTik по принятой схеме). Без согласования не внедрять DNS hijack, fake-IP, SNI sniffing, изменения DNS роутера.
- При испытаниях сохранять приоритетный административный канал **MikroTik SSTP** и SSH, доступ к LAN. IP нового тестируемого VPN-сервера должен идти DIRECT, не через SSTP/другой VPN. **MikroTik, действующую microSD и продуктивный шлюз без отдельного разрешения не трогать.**
- Подписки/ключи/токены не копировать в публичный GitHub или диагностический вывод.

## 3. Что доказано и чего НЕ доказано (2026-10-18)

- Рабочая **старая microSD** принята как поведенческий эталон. **`awg-upgrade-test` — тестовая microSD**, не следует считать её идентичной эталону.
- Отдельная проверенная резервная копия тестового состояния: проверены поток, **31/31 обязательных компонентов, 74 установленныx цели**, 97 файлов, 112 записей, Hot Pool и Stage18. Архив изолированно распакован; 97/97 SHA-256, владельцы и права совпали; статические связи systemd и наличие файлов состояния проверены. **Это не равно полноценному восстановлению шлюза на чистой ОС.** Этап резервирования сейчас **закрыт/поставлен на паузу**; больше не развивать без блокирующей причины.
- На тестовой Pi обнаружено состояние `awg-quick@awg0.service=failed` из-за отсутствия `/etc/amnezia/amneziawg/awg0.conf`; это известное ограничение тестового стенда, **не доказательство дефекта релиза** и не подтверждение работоспособного AWG-резерва.
- **PR #115** (`feature/v1.3-complete-media-install-20261017`, HEAD после правок `b50712e`) — **draft/open**, не релиз. По описанию PR тесты кода прошли (204/204 и смежные), но **реальная установка на пустую microSD с конечными профилями, резервом, LAN, перезагрузкой НЕ пройдена**. PR основан на review-ветке #113 и требует согласования с develop/main; #113 и #114 также review/draft на момент среза.
- **Доработка 2026-10-18 в draft PR #115:** для автоматического выбора транспорта добавлена проверка существования непустого `awg0.conf` до попытки запуска резервного AWG. При отсутствующем профиле больше не должны выполняться повторные `awg-quick`-старты; настроенный холодный резерв по-прежнему запускается штатным preflight. В коде READY TUN postcheck уже есть `curl -q --noproxy '*'`, а регрессионные тесты на эти флаги и отсутствие AWG-профиля добавлены. **26 адресных + 6 gate-тестов прошли на тестовой Pi в unprivileged fixture**; один отдельный root-ориентированный тест `test_ready_auto_persistence.py` не удалось полноценно прогнать через удалённый интерфейс без `sudo`. **Установлено на тестовой Pi 2026-10-18 в 09:48 (+07):** файлы `/usr/local/sbin/awg-selection-monitor` и `/usr/local/sbin/awg-mihomo-ready-postcheck-tun` совпадают с HEAD PR #115 `b50712e`, `root:root 0755`, монитор перезапущен и `active`. После рестарта новых попыток `awg-quick@awg0` без профиля не наблюдалось (наблюдение, не длительный стресс-тест). Проверен текущий Pi-bound `mihomo0`: `curl -q --noproxy '*'` через интерфейс к OpenAI API вернул HTTP 401; таблица 100 указывает на `mihomo0`. Hot Pool продолжает обновляться; в 09:47 было 3 READY при цели 4. **Фактическое значение защищённой политики `ready-auto` не прочитано удалённым диагностическим подключением; LIVE READY→TUN/rollback, AWG failover и LAN-клиент не испытаны.** `ChatGPT Web=UNKNOWN` только при подтверждённом HTTP 403 допустим для MEDIUM_NETWORK_CONFIDENCE вместе с OpenAI API PASS и реальным YouTube24 PASS, но не доказывает работу авторизованного ChatGPT.
- **PR #116** с `AGENTS.md` и `docs/INSTALLER-CHANGE-POLICY.md` уже merged в `main`. Текущий стабильный тег в README — **v1.2.0**; **v1.3.0 не объявлять стабильным**, пока gate не закрыт.

## 4. Очередность оставшейся работы (не менять без причины)

1. Сверить PR #115 и реальную сборку на тестовой microSD с **работающей старой microSD**, устранить только выявленные расхождения в installer/upgrade и тестах. Проверить обязательные медиа-зависимости, ввод/замену профилей после установки, восстановление Stage18 из постоянного кэша.
2. На **чистой отдельной Debian 13 ARM64 microSD** проверить полный инсталлятор: оба движка заранее, ввод AWG и/или Mihomo после установки, подписка/адаптеры, Hot Pool, READY и выбор/проверка ноды; без ручной доустановки обязательных компонентов.
3. Выполнить контролируемые реальные проверки: HTTPS ChatGPT/OpenAI, **YouTube decode**, TUN, отдельный **LAN-клиент**, смена ноды, отказ Mihomo → доступный AWG, `NO_WORKING_TRANSPORT`/FAIL-CLOSED, восстановление, защита SSTP/SSH, reboot/persistence; без теста нельзя ставить PASS.
4. Проверить upgrade с v1.2.0, откат, CI; перенести проверенные изменения в версионированный installer и develop/main через согласованные PR; **только после аппаратных acceptance gates выпускать v1.3.0**.

## 5. Обязательный протокол следующей работы

1. В начале разговора прочитать **этот файл**, `AGENTS.md`, `docs/INSTALLER-CHANGE-POLICY.md`, `docs/TESTING-v1.3.0.md` и актуальные PR/состояние Pi при необходимости. Не выдавать этот срез за текущую телеметрию.
2. Начинать с **главной цели → текущий этап → ближайший блокер**, а не с новой вспомогательной идеи. Не задавать вопросы, ответы на которые уже есть в проекте.
3. Действовать самостоятельно доступными инструментами (GitHub/удалённая Pi), когда безопасно и разрешено. Любой меняющий транспорт/маршруты тест — только с согласованной защитой доступа. Различать «запланировано», «в PR», «на тестовой Pi», «на production», «в stable».
4. После существенного результата обновлять **только проверенные факты** и статус следующего шага здесь; детали доказательств — в тестовой документации/PR. **Не плодить новые планы и документы вместо завершения шлюза.**
